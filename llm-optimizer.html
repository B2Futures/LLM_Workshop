How this works & glossary

How to use this tool

1. Choose Desktop or Server mode. Desktop is for running models on your own machine. Server is for planning or optimizing a machine others will access — all fields are manual since your current computer is irrelevant.

2. Enter your hardware. On desktop, click Detect to pre-fill what the browser can read, then confirm or correct VRAM and RAM manually. On server, enter the target machine specs directly.

3. Find compatible models. Model cards appear with fit indicators showing what runs well, what's tight, and what won't fit. Headroom shown is VRAM remaining after the model loads — that's what's available for context (KV cache).

4. Select a model. Click the card for what you are actually running. If it's not listed, use the Custom model entry below the cards.

5. Select your app and click Generate. Recommendations are tuned to that specific model on your hardware in your app — not just generic GPU advice.

6. Sampling presets appear at the bottom — pick the preset that matches your use case for output quality settings.

General terms

VRAM (Video RAM)
Memory on your graphics card. Model weights and working data live here during inference. More VRAM = bigger models and longer conversations. Completely separate from system RAM.
Model weights
The data that makes up an AI model — billions of numbers learned during training. Loading a model means reading these weights into VRAM. A 12B Q4_K_M model uses roughly 7–8 GB of VRAM just for weights before any conversation starts.
Quantization (Q4, Q5, Q6, Q8)
Compression that reduces the precision of model weights to save memory. Q4 uses 4 bits per value, Q8 uses 8 bits. Lower = smaller and less VRAM but slightly lower quality. Q4_K_M is the most common sweet spot. Q8 is near full quality. F16 is full precision — largest, best quality.
Inference
Running a model to generate a response. Every message and reply is an inference.
Token / tok/s
The basic unit of text — roughly 3/4 of a word. Tok/s is generation speed. 10–20 tok/s feels like comfortable reading speed. Below 3 tok/s starts to feel slow. GPU inference is typically 10–100x faster than CPU-only.
VRAM headroom
VRAM remaining after model weights are loaded. This headroom is what powers your context window (KV cache). More headroom = longer conversations and faster processing.

Settings terms

GPU Layers / n_gpu_layers
How many layers of the model to run on GPU. Setting to -1 or max means fit as many as VRAM allows. More layers on GPU = faster generation. If VRAM runs out the app crashes or slows — reduce until stable.
Context length / n_ctx
Maximum tokens the model can see at once — your prompt plus conversation history plus the response. Larger = longer conversations but consumes more VRAM via the KV cache. The tool calculates your safe maximum based on actual headroom.
KV cache
Stores intermediate calculations for every token so they are not recomputed. Lives in VRAM and grows as conversations get longer. KV cache quantization (Q8, Q4) compresses it to save VRAM with minimal quality impact.
Batch size / n_batch
How many tokens are processed in parallel when reading your prompt. Larger = faster prompt ingestion but more VRAM. Does not affect generation speed (tok/s).
Flash attention
A more memory-efficient attention computation. Reduces VRAM usage and speeds up long contexts. Safe to enable — no quality change. Works on CUDA, Metal, and Vulkan.
Mmap / Mlock
Mmap = memory-mapped file loading — faster model load times. Mlock = pins the model in RAM so the OS cannot swap it to disk — prevents slowdowns but requires enough RAM to hold the full model.
RoPE scaling
A technique to extend a model's context beyond what it was trained on. A model trained at 4K context can be pushed to 32K with RoPE scaling, with some quality degradation at very long ranges.
Backend (CUDA / ROCm / Metal / Vulkan)
The software layer connecting the LLM app to your GPU. CUDA = NVIDIA native (fastest on NVIDIA). ROCm = AMD native on Linux. Metal = Apple GPU. Vulkan = cross-platform fallback — works on most GPUs but slower than native options.

Sampling terms

Temperature
Controls randomness. 0 = always pick the most likely word (deterministic). 1 = sample normally. Higher = more creative and unpredictable. For coding or factual tasks, use low values (0.1–0.3). For creative writing, use higher (0.8–1.2).
Top-P (nucleus sampling)
Limits token selection to the smallest set of top candidates whose probabilities sum to P. At 0.95, the model only considers tokens that collectively account for 95% of the probability mass. Filters out unlikely garbage tokens.
Min-P
A newer alternative to Top-P. Filters out tokens whose probability falls below a minimum threshold relative to the top token. Often produces more coherent output than Top-P at the same settings.
Top-K
Limits token selection to the K most likely candidates at each step. Lower = more focused, higher = more variety. Often used alongside Top-P.
Repeat penalty
Penalizes the model for repeating tokens it already used. Values above 1.0 discourage repetition. Too high causes avoidance of common words. 1.05–1.15 is a safe range.
Seed
A number that fixes the random starting point for generation. Same seed + same prompt = same output every time. Useful for reproducible testing. -1 = random each time.
Max tokens / n_predict
Hard cap on response length. -1 = unlimited (model decides when to stop). Set a value to prevent very long runaway responses.

Server-specific terms

Concurrent users / parallel slots
How many requests are processed simultaneously. Each active request needs its own KV cache in VRAM — more users = more VRAM consumed regardless of model size.
Continuous batching
Processes multiple requests in overlapping batches rather than sequentially. Dramatically improves throughput when many users are active simultaneously. Automatic in vLLM, TGI, and llama.cpp server.
Throughput vs latency
Throughput = total tokens per second across all users. Latency = how long one user waits. Server deployments usually optimize throughput; desktop optimizes latency. You cannot fully maximize both simultaneously.
Tensor parallelism
Splits each model layer across multiple GPUs simultaneously. Best for large models that do not fit on one card. Requires fast GPU interconnects — NVLink ideal, PCIe works but is slower.
PagedAttention / prefix caching
Used in vLLM — manages KV cache like virtual memory. Multiple users sharing the same system prompt reuse cached computations. Saves significant VRAM in production deployments.
vLLM / TGI / llama.cpp server
Server frameworks for hosting LLMs. vLLM optimizes for high throughput with PagedAttention. TGI (Hugging Face) is production-hardened with built-in monitoring. llama.cpp server is lightweight and works on consumer hardware. All expose an OpenAI-compatible API.
